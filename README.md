# tuya-stress

Утилита для стресс-тестов Tuya-устройств по локальному протоколу (версии 3.3, 3.4, 3.5)
в обход Home Assistant.

Нужна, чтобы найти, от чего зависает устройство: от долгого соединения, от количества
команд, от частоты обращений или от чего-то ещё. Утилита шлёт устройству команды или
запросы, пока оно не перестанет отвечать, и сообщает, сколько операций и сколько времени
оно продержалось.

## Подготовка

### 1. Отключите устройство в Home Assistant

Многие Tuya-устройства держат **только одно** локальное подключение. Если tuya-local
подключена к устройству, утилита либо не сможет подключиться, либо будет мешать
интеграции и наоборот, и результаты потеряют смысл.

В Home Assistant: *Настройки → Устройства и службы → Tuya Local → нужное устройство →
⋮ → Отключить*.

Также закройте приложение Smart Life / Tuya на телефонах в той же сети.

### 2. Узнайте параметры подключения

Понадобятся:

| Что | Где взять |
|---|---|
| **Device ID** | в настройках устройства в tuya-local, в приложении Smart Life (*устройство → ✎ → Информация об устройстве → Виртуальный ID*), через `tinytuya wizard` |
| **IP-адрес** | в настройках tuya-local или в списке клиентов роутера |
| **Local key** | в настройках устройства в tuya-local или через `tinytuya wizard` |
| **Версия протокола** | та же, что выбрана в tuya-local: 3.3, 3.4 или 3.5 |

Local key меняется при каждой новой привязке устройства к приложению. Если вы
перепривязывали устройство, возьмите актуальный ключ.

> Не публикуйте local key (например, в issues на GitHub): он даёт полное управление
> устройством из вашей локальной сети.

### 3. Закрепите IP-адрес

Если роутер выдаст устройству другой адрес посреди теста, это будет выглядеть как
зависание. Сделайте резервирование DHCP для устройства.

## Сборка

Нужен Rust 1.87 или новее ([rustup.rs](https://rustup.rs)).

```
cargo build --release
```

Готовый файл: `target/release/tuya-stress` (на Windows — `target\release\tuya-stress.exe`).

Можно запускать и через cargo, тогда параметры программы пишутся после `--`:

```
cargo run --release -- --id DEVICE_ID --ip 192.168.0.10 --key "LOCAL_KEY" --version 3.3
```

## Запуск

Минимальная команда:

```
tuya-stress --id DEVICE_ID --ip 192.168.0.10 --key "LOCAL_KEY" --version 3.3
```

**Local key всегда берите в кавычки.** В ключах часто встречаются символы вроде
`# ) ? ! ]`, которые PowerShell и bash иначе поймут по-своему.

В PowerShell, если в ключе есть `$` или `` ` ``, используйте одинарные кавычки:
`--key '4E!)#Z)$J7L?]lw1'`.

Остановить тест в любой момент: **Ctrl+C**.

Для долгих тестов пишите лог в файл: консоль IDE хранит ограниченное число строк,
а самое интересное (начало деградации) может вытесниться:

```
tuya-stress --id DEVICE_ID --ip 192.168.0.10 --key "LOCAL_KEY" --version 3.3 --verbose --log test1.log
```

Файл пишется сразу после каждой строки, так что лог сохранится, даже если тест прервать.

## Параметры

### Подключение

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--id` | — | Device ID (обязательный) |
| `--ip` | — | IP-адрес или имя устройства (обязательный) |
| `--key` | — | local key, ровно 16 символов (обязательный) |
| `--version` | `3.4` | версия протокола: `3.3`, `3.4` или `3.5` |
| `--port` | `6668` | TCP-порт устройства |
| `--timeout` | `5` | сколько секунд ждать подключения и ответа |

### Нагрузка

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--mode` | `persist` | `persist` — одно постоянное соединение, `reconnect` — новое на каждую операцию |
| `--read-only` | выкл. | только запрашивать статус, ничего не записывать |
| `--dp` | `114` | номер dp, в который пишутся значения |
| `--values` | `10,15` | значения через запятую, по очереди: числа, `true`/`false`, строки |
| `--interval` | `5` | пауза между операциями, секунд (можно дробные: `0.5`; `0` — без пауз) |
| `--wait-status` | выкл. | после подтверждения команды ждать от устройства отчёта о новом состоянии и только потом слать следующую |

### Завершение и вывод

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--fail-limit` | `5` | сколько ошибок подряд считать зависанием |
| `--max-ops` | — | остановиться после N успешных операций |
| `--verbose` | выкл. | печатать каждую операцию, отчёты о состоянии и пакеты, которые устройство прислало само («прочее») |
| `--log` | — | дублировать вывод в файл; если файл уже есть, дописывается в конец |

Полный список: `tuya-stress --help`.

## Что выводит программа

```
[2026-11-06 22:06:33 t=1794024393 +0.0 мин] старт: устройство=192.168.0.10 протокол=3.3 режим=Persist ...
[2026-11-06 22:06:33 t=1794024393 +0.0 мин] подключено (подключений: 1)
[2026-11-06 22:06:33 t=1794024393 +0.0 мин] успешно: 1 (подключений: 1)
[2026-11-06 22:07:33 t=1794024453 +1.0 мин] успешно: 13 (подключений: 1)
...
[2026-11-06 23:20:51 t=1794028851 +74.3 мин] #890 ОШИБКА: таймаут ответа
...
[2026-11-06 23:21:09 t=1794028869 +74.6 мин] Устройство не отвечает: 890 успешных операций за 74.6 мин, отказов устройства: 0, подключений: 3
```

Метка времени в начале строки:

- **дата и локальное время** — чтобы сопоставлять с логами Home Assistant;
- **`t=`** — unix-время, в тех же единицах, что поле `"t"` в отчётах устройства;
- **`+74.3 мин`** — сколько прошло от старта теста.


- **подключено** — открыто TCP-соединение (в режиме `reconnect` не печатается без `--verbose`);
- **успешно: N** — сколько операций прошло; печатается после первой операции и затем
  раз в минуту;
- **ОШИБКА** — устройство не ответило или соединение оборвалось; печатается сразу,
  `#890` — сколько успешных операций было к этому моменту. После ошибки программа
  переподключается, и только ошибки подряд считаются зависанием;
- **ОТКАЗ** — устройство ответило, но отказалось выполнять команду (например,
  `data format error`). Соединение при этом сохраняется, и это не считается зависанием;
- **итоговая строка** — главный результат теста.

**Тишина между строками прогресса — это нормально**: ошибки печатаются сразу, так что
если их нет, команды проходят.

В итоговой строке также указано число отказов.

Коды завершения: `0` — достигнут `--max-ops`, `1` — устройство перестало отвечать,
`2` — неверные параметры.

## Режимы

### `persist` — как tuya-local

1. Один раз подключается и держит соединение открытым.
2. Через каждые `--interval` секунд отправляет команду в это же соединение.
3. Ждёт подтверждения от устройства.
4. При ошибке закрывает соединение и в следующий раз подключается заново.

### `reconnect` — новое соединение на каждую операцию

То же самое, но перед каждой операцией открывается новое соединение, а после неё
закрывается. Так устройство никогда не держит соединение дольше нескольких сотен
миллисекунд.

### `--read-only` — только чтение

Вместо записи отправляется запрос статуса всех dp. Комбинируется с любым режимом.

## Сценарии стресс-тестов

Примеры даны для Tion Bio X (dp 114 — температура нагрева) на протоколе 3.3. Для другого
устройства подставьте свой dp и допустимые значения.

**Общие правила:**

- запускайте каждый тест **до зависания**;
- перед каждым тестом **перезагружайте устройство по питанию**, чтобы все тесты
  стартовали с одинакового состояния;
- **сравнивайте тесты с одинаковым `--interval`**, кроме теста 4, где интервал и есть
  предмет проверки;
- следите, чтобы компьютер **не уходил в сон**: оборвавшееся соединение испортит результат.

Для краткости ниже `$DEV` означает
`--id DEVICE_ID --ip 192.168.0.10 --key "LOCAL_KEY" --version 3.3`.

### Тест 0. Проверка связи

```
tuya-stress $DEV --max-ops 3 --verbose
```

Должно напечатать три успешные операции. Посмотрите на устройство: значение должно
меняться. Если нет — см. [Если что-то не работает](#если-что-то-не-работает).

### Тест 1. Базовый: постоянное соединение и запись

```
tuya-stress $DEV --mode persist --values 0,5 --interval 1 --fail-limit 30
```

**Вопрос:** воспроизводится ли зависание без Home Assistant?

- **виснет** — проблема в прошивке устройства, а не в tuya-local;
- **не виснет** за несколько часов — проблема связана с поведением интеграции
  (heartbeat, опрос, частые переподключения).

Число операций до зависания из этого теста — точка отсчёта для остальных.

### Тест 2. Новое соединение на каждую команду

```
tuya-stress $DEV --mode reconnect --values 0,5 --interval 1 --fail-limit 30
```

**Вопрос:** зависит ли зависание от времени жизни соединения?

- **живёт заметно дольше**, чем в тесте 1, — утечка привязана к соединению.
  Периодическое переподключение (например, в форке tuya-local) может решить проблему;
- **виснет примерно так же** — проблема в обработке самих команд, переподключение
  не поможет.

### Тест 3. Только чтение

```
tuya-stress $DEV --mode persist --read-only --interval 1 --fail-limit 30
```

**Вопрос:** вредят ли устройству любые обращения или только запись?

- **виснет** — «изнашивает» любой обмен сообщениями, даже опрос статуса;
- **не виснет** — проблема только в командах записи.

### Тест 4. Реже команды

```
tuya-stress $DEV --mode persist --values 0,5 --interval 5 --fail-limit 30
```

Сравните с тестом 1 (там `--interval 1`):

- зависание после **примерно того же числа операций** — дело в количестве команд;
- зависание примерно **через то же время** — дело во времени, а не в нагрузке
  (например, во времени жизни соединения).

### Тест 5. Перегрузка (необязательный)

```
tuya-stress $DEV --mode persist --values 0,5 --interval 0.2 --fail-limit 60
```

Проверяет реакцию на очень частые команды. Многие Tuya-устройства от этого уходят
в офлайн на 30 секунд — несколько минут и **возвращаются сами**. Это не то зависание,
которое мы ищем, но полезно знать порог. Поэтому здесь большой `--fail-limit`:
программа переждёт временное отключение.

### Тест 5а. Максимальная частота с ожиданием отчёта о состоянии

```
tuya-stress $DEV --mode persist --values 0,5 --interval 0 --fail-limit 60
tuya-stress $DEV --mode persist --values 0,5 --interval 0 --fail-limit 60 --wait-status
```

После команды устройство сначала присылает подтверждение, а затем отдельным пакетом
отчёт о новом состоянии. Без `--wait-status` следующая команда уходит сразу после
подтверждения, пока устройство, возможно, ещё не закончило с предыдущей.

- **отказы `data format error` пропадают с `--wait-status`** — устройство не умеет
  принимать команду, пока не отправило отчёт о предыдущей;
- **отказы остаются** — дело в чём-то другом (например, в частоте самой по себе).

### Тест 6. Разные значения и dp

```
# три значения по кругу
tuya-stress $DEV --values 0,5,10 --interval 1 --fail-limit 30

# логический dp, например вкл/выкл звука (dp 103 у Tion Bio X)
tuya-stress $DEV --dp 103 --values true,false --interval 1 --fail-limit 30
```

Помогает понять, зависит ли проблема от конкретного dp.

## Как вести учёт результатов

После каждого теста записывайте:

| Тест | Параметры | Операций до зависания | Время, мин | Пингуется после? | Ожил сам? Через сколько? |
|---|---|---|---|---|---|
| 1 | persist, 1 с | | | | |
| 2 | reconnect, 1 с | | | | |
| 3 | persist, read-only, 1 с | | | | |
| 4 | persist, 5 с | | | | |

**Пингуется ли после зависания:**

- **не пингуется** — модуль завис целиком или выпал из Wi-Fi;
- **пингуется, но не отвечает** — перестал принимать соединения на порту 6668,
  сам модуль жив.

**Ожил ли сам:** подождите 10–15 минут, прежде чем перезагружать. Если устройство
вернулось само — это скорее перегрузка или watchdog, если нет — настоящее зависание.

Каждый тест желательно повторить 2–3 раза: разброс между прогонами покажет, насколько
результаты стабильны.

## Если что-то не работает

**Таймаут на первой же операции**

- неверная версия протокола — попробуйте 3.3, 3.4 и 3.5 по очереди;
- неверный local key — устройство с чужим ключом обычно просто молчит;
- устройство всё ещё подключено к Home Assistant или к приложению на телефоне;
- в PowerShell ключ передан без кавычек и испортился.

**«согласование ключа: не сошёлся HMAC»** — неверный local key (протоколы 3.4/3.5).

**ОТКАЗ «устройство вернуло код N»** — устройство приняло пакет, но отказалось
выполнять команду. Если это происходит всегда — скорее всего, такого dp нет или
значение вне допустимого диапазона. Если только изредка и при высокой частоте —
устройство не успевает обрабатывать команды, см. тест 5а.

**Ошибка подключения сразу** (`Connection refused`, `No route to host`) — неверный IP,
устройство выключено или в другой подсети.

**Значение на устройстве не меняется, но ошибок нет** — проверьте `--dp`: возможно,
у вашего устройства этот dp означает что-то другое.

## Структура проекта

```
src/
├── main.rs          точка входа
├── cli.rs           параметры командной строки
├── stress.rs        цикл стресс-теста
├── lib.rs           библиотека (не зависит от CLI)
└── tuya/
    ├── mod.rs       публичный интерфейс модуля
    ├── consts.rs    номера команд, маркеры пакетов
    ├── version.rs   версии протокола
    ├── crypto.rs    AES-ECB, AES-GCM, HMAC-SHA256
    ├── frame.rs     сборка и разбор пакетов (без сети)
    ├── session.rs   согласование сеансового ключа 3.4/3.5
    ├── conn.rs      TCP-соединение и команды: set_dp, query, heartbeat
    └── error.rs     тип ошибок
tools/
└── fake_device.py   эмулятор устройства для проверки без железа
```

Модуль `tuya` можно использовать отдельно:

```rust
use tuya_stress::tuya::{Connection, DeviceConfig, Version};

let cfg = DeviceConfig::new("DEVICE_ID", "192.168.0.10", None, "LOCAL_KEY_16CHAR", Version::V33)?;
let mut conn = Connection::open(&cfg)?;
println!("{}", conn.query()?);
conn.set_dp(114, &serde_json::json!(20))?;
```

## Проверка без устройства

Юнит-тесты сверяют сборку пакетов и вычисление сеансовых ключей с эталонами из tinytuya:

```
cargo test
```

Для проверки целиком есть эмулятор устройства (нужен Python и `pip install tinytuya`):

```
# версия протокола, порт, [после скольких команд «зависнуть»], [отклонять каждую N-ю команду]
python3 tools/fake_device.py 3.3 7000 30

# в другом окне
tuya-stress --id dev123 --ip 127.0.0.1 --port 7000 --key 0123456789abcdef --version 3.3 --interval 0.1
```
